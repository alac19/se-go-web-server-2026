## 一、引言

### 1.1 项目背景
本项目是在已完成 Rust 高并发 Web 服务器（反向代理）的基础上，使用 Go 语言进行重构，保持原有核心功能的同时，增加容器化部署、配置热重载等现代云原生特性。目标是实现一个高性能、可观测、易维护的 HTTP/HTTPS 反向代理服务器。

### 1.2 项目目标
- 完全兼容原有 Rust 版本的功能：HTTP/HTTPS 双协议监听、轮询负载均衡、后端健康检查、日志记录。
- 提升工程化能力：模块化代码组织（config / lb / health）、单元测试、Docker 容器化。
- 支持配置热重载（监听 config.toml 变化，无需重启进程）。
- 提供清晰的压测报告，对比 Go 与 Rust 版本的性能差异。

### 1.3 适用范围
本文档适用于本项目的需求分析、设计、开发和测试阶段，作为所有技术决策的依据。

### 1.4 用户角色
- **客户端**：发起 HTTP/HTTPS 请求的浏览器、curl 或其他服务。
- **运维人员**：通过日志监控代理状态，修改配置文件。

### 1.5 假定与约束

- **假定 1**：后端服务必须提供 `/heartbeat` 健康检查端点，且返回 HTTP 200 表示健康。
- **假定 2**：证书文件 `cert.pem` 和 `key.pem` 由使用者自行生成（项目提供 `openssl` 命令示例）。
- **约束 1**：本项目不涉及数据库、消息队列或微服务注册中心。
- **约束 2**：开发环境 Go 1.25+，生产环境建议 Linux + Docker。
- **约束 3**：配置热重载（FR-08）为可选功能，若时间不足可暂缓实现，不影响核心功能交付。

## 二、功能性需求

| 编号  | 需求描述                                                                                                                             | 优先级 |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------ | ------ |
| FR-01 | **双协议监听**：同时监听 HTTP和 HTTPS 端口，TLS 使用自签名证书（cert.pem / key.pem）。                                               | 高     |
| FR-02 | **反向代理转发**：接收客户端请求，将其转发到配置文件中定义的后端服务列表。                                                           | 高     |
| FR-03 | **负载均衡**：采用轮询（Round‑Robin）算法，原子操作保证线程安全。                                                                    | 高     |
| FR-04 | **健康检查**：启动时及后台定期（如每 30 秒）请求每个后端的 `/heartbeat` 路径，根据响应状态码（2xx）判断健康状态，自动剔除/恢复后端。 | 高     |
| FR-05 | **配置管理**：使用 TOML 格式配置文件（`config.toml`），包含监听地址/端口、后端地址/端口、心跳路径/间隔/超时等。                      | 高     |
| FR-06 | **日志记录**：记录每个请求的方法、路径、耗时、转发到的后端地址；错误日志单独记录。输出格式为 JSON（使用 `log/slog`）。               | 高     |
| FR-07 | **错误处理**：当所有后端均不可用时，返回 503 Service Unavailable；当单次转发失败时，返回 502 Bad Gateway。                           | 高     |
| FR-08 | **配置热重载**（可选）：监听 `config.toml` 文件变化（如使用 `fsnotify`），或支持 SIGHUP 信号触发重载，更新后端列表而不重启进程。     | 中     |

## 三、非功能性需求

| 编号   | 需求描述                                                                                                                | 指标 / 约束                              |
| ------ | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| NFR-01 | **性能**：在本地环境（或同机后端）下，能处理 ≥ 5000 并发连接，平均响应时间 < 10ms（静态测试）。                         | 使用 `wrk` 或 `hey` 验证                 |
| NFR-02 | **可靠性**：定期健康检查，自动剔除异常后端；所有错误必须有日志记录和合理 HTTP 状态码。                                  | 无单点故障（单个后端挂掉不影响整体服务） |
| NFR-03 | **可维护性**：代码按 `config`、`lb`、`health` 包组织，每个包有独立的单元测试（`go test`）。                             | 测试覆盖率 ≥ 60%                         |
| NFR-04 | **安全性**：TLS 配置最低版本 TLS 1.2，禁用弱加密套件；不记录敏感信息（如请求体）。                                      | 使用 `sslscan` 或 `testssl.sh` 可检查    |
| NFR-05 | **可移植性**：提供 `Dockerfile`（多阶段构建），镜像大小 ≤ 30MB；提供 `docker-compose.yml` 一键启动代理 + 三个模拟后端。 | 能通过 `docker compose up` 运行。        |
| NFR-06 | **兼容性**：可在 Windows（开发）、Linux（部署）下运行，使用 Go 标准库确保跨平台支持。                                   | 在 WSL2 或 Linux 虚拟机中验证            |
